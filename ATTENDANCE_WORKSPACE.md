# Attendance browser and transaction increment

Operators open **Attendance** in the actual browser application. Search class/date sessions with 25-row paging, or choose **New session**, select a class with current active students, date, Morning/Afternoon/Full day, expected count and optional notes. At creation, the service locks and captures the then-active students in that class, including encrypted name, Pris No. and status. Attendance lookup and record validation use this captured roster, so later transfers, deactivation or profile edits do not rewrite who was captured for the session. The snapshot is taken when the session is created; creating a session retrospectively does not reconstruct class membership on the attendance date. The active class count remains a starting value for expected count; the operator verifies it against the register. One class/date/session-type combination is permitted, including closed sessions.

An Operator can also load classes scheduled on the selected date from a currently published timetable, using the academic year and session date. The form shows mapped instructional classes with their lessons and current active-student count, and pre-fills the student profile class. Creating this kind of session stores the published timetable version and instructional class IDs as immutable provenance. The API rechecks that the publication is still current, covers the date, has a lesson for that class/day, and matches an active attendance class mapping. Manual session creation remains available for work outside a published timetable and has no timetable provenance.

IT Administrators maintain a dedicated attendance class mapping between a student profile's `class_name` and one instructional timetable class. Each side can appear in at most one active mapping; changes are versioned and audited. This mapping is independent of the Student Intake 2023 source-label crosswalk. Mapping counts are calculated from current active profiles and are only a starting point for the operator's register check.

Open a session to review its captured roster, entered records, unentered expected records and records explicitly marked MISSING. Search the captured roster (25 displayed; refine when more match), select a student and save PRESENT, ABSENT, LATE, EXCUSED or MISSING. The backend validates roster membership, duplicate records, session state and expected-count capacity. The roster snapshot is the authorization/eligibility boundary. Saved notes and correction reasons render as text. Legacy sessions are explicitly marked `LEGACY_PARTIAL`; migration can preserve roster membership only for students with existing attendance records, so these sessions cannot claim a complete historical roster.

Corrections keep the same student identity and require a new nonblank reason. Both the previous and new values/version are audited. A stale save keeps entered form values and requires **Reload session** to load the winning change; it never overwrites another operator's update. An expected-count adjustment requires a reason and cannot go below entered records. It is audited and versioned, allowing a deliberate count correction before adding more students.

Close a complete session normally. If records are unentered or marked MISSING, closure returns 409 unless the operator explicitly checks **Close incomplete attendance** and supplies a reason. Closed sessions are read-only and cannot be reopened or silently changed in this increment. The dashboard missing figure now includes both unentered expected records and explicit MISSING marks. Refresh the dashboard to see committed attendance.

## API and concurrency contract

Migration `20261026_0007` adds version=1 to existing sessions and records, and a unique class/date/type session index. It checks duplicate or untrimmed legacy sessions before DDL and fails with an explicit reconciliation requirement if found. Migration `20261028_0012` adds encrypted roster snapshots for new sessions and backfills only students already represented by attendance records as `LEGACY_PARTIAL`; it does not infer unrecorded historical students or change existing profile/attendance ciphertext. For backfilled entries, the name is copied from the current profile at migration time because legacy records did not preserve a name. Clean existing fields, attendance and reasons are preserved. Downgrades refuse destructive removal of the version/uniqueness and snapshot guarantees.

- `POST /attendance/sessions` retains date/type/class/expected-count/notes, captures the active class roster in the same transaction and returns a session version plus snapshot state. Duplicate concurrent creation returns 409 through the database index.
- `GET /attendance/scheduled-classes?academic_year=2026&session_date=2026-10-26` returns mapped classes with lessons on that date in the one current publication for that year/week.
- `POST /attendance/sessions` accepts both `timetable_version_id` and `instructional_class_id` together for a published-timetable session; one without the other is rejected. These IDs remain nullable for manual sessions. Migration `20261103_0014` adds the dedicated attendance mapping table and nullable session provenance while preserving existing session and roster data.
- `GET/POST /student-reference/attendance-class-mappings` and `PATCH /student-reference/attendance-class-mappings/{id}` provide IT-managed mapping maintenance, active-student counts, optimistic version checks and audit events. The operator role can read mappings; only IT Administrator and Superuser can create/update them.
- `GET /attendance/sessions` accepts class/date filters, offset and limit (default/max 100), returning the existing list shape. Invalid reversed date ranges return 422.
- `GET /attendance/sessions/{id}` returns the session, captured roster, records and missing/marked-missing counts from a consistent session-locked read. Roster entries include captured identity/status and any saved mark. The existing `/records` endpoint returns records with record/session versions and captured identity.
- `POST /attendance/sessions/{id}/records` now requires `expected_session_version` alongside Pris No., mark and optional nonblank reason. A save increments the session version; the new record begins at version 1.
- `PATCH /attendance/records/{id}` now requires `expected_session_version`, record `expected_version`, the unchanged Pris No., mark and a nonblank correction reason. It advances both versions atomically.
- `PATCH /attendance/sessions/{id}` accepts `expected_version`, revised `expected_count` and reason. The class/date/type identity is immutable.
- `POST /attendance/sessions/{id}/close` now requires a JSON body with `expected_version`; optional `allow_incomplete=true` also requires a reason. It advances the session version and freezes normal API amendments.

These version fields/close bodies are required changes for clients of the original foundation API. PostgreSQL row locks serialize writes/read grids by session, and version comparisons reject stale clients. Session creation locks the selected active student rows while capturing the roster; attendance writes lock the selected student row and require a session roster entry, even if the student's current profile later changes. Duplicate/capacity/close checks run under the session lock. Record, session revision, audit and closure/count changes commit or roll back together; write responses are captured before releasing the transaction. SQLite is a migration/development convenience, not the proof of these production locking guarantees.

Raw session/record APIs now deny Executive access; Executives retain dashboard/report access. Support/bootstrap API roles retain the foundation's broader access pending complete permission-matrix hardening. Browser daily attendance controls are Operator-only. Sign-out, expiry or revoked-access responses clear attendance records, eligible lists and forms; old request/selection results cannot restore them.

## Boundaries and verification

The monthly Excel register now uses the union of session roster snapshots and saved attendance for that month, retaining students who later moved or became inactive. The workbook labels legacy partial snapshots and notes that their names reflect migration-time profiles; it labels the fallback to current active profiles when no sessions exist in that month. A snapshot records membership at session creation, not date-effective enrollment; retroactive creation and historical class/status reconciliation still require explicit business handling. Attendance granularity policy (including mixing FULL_DAY with other types), reopening/historical corrections, visual/formula parity with the legacy workbook and complete permission hardening remain required before cutover. No claims of full legacy reporting parity or production readiness follow from these screens.

CI adds lifecycle/missing/closure tests, duplicate session and record/close races, concurrent corrections, identity/reason/version checks, count controls, Executive denial and transaction-failure rollback. Migration rehearsals verify legacy roster rows are preserved as partial without rewriting student ciphertext, and refuse ambiguous duplicate sessions without deleting data. API/browser tests prove that later transfer, deactivation and renaming do not change a captured roster or its monthly export. Chromium tests also exercise new-session prompts, lookup, marks, corrections, count adjustments, explicit incomplete closure, dashboard updates, stale forms/reload, duplicate sessions and sign-out clearing. The production image check includes the local attendance module; all prior browser, API, migration and security gates continue to run.
