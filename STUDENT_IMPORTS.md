# Student Intake workbook import

Operators can import `Student Intake 2021` or `Student Intake 2023` from **Student profiles**. The Operator selects the source year explicitly; this is required because the supplied workbook contains both tabs, and the 2021 worksheet is hidden in the workbook. The parser reads only the exact selected sheet using its version-specific header map, ignores `S/N` as a row sequence, maps `PRIS NO`/`Pris No.` to the unique student key, and resolves the selected sheet's `CLASS`/`INSTN CLASS` through that year's separate IT-managed class crosswalk. The student's class is stored using the canonical instructional-class name. Unknown or missing required headers reject the workbook rather than silently dropping data. Import batches retain the selected source version.

## Upload, preview and commit

1. The browser posts the selected `.xlsx` bytes directly to `POST /api/v1/student-imports?source_workbook=...`; it does not send the workbook to a third-party service or write an upload file to the app's temporary directory.
2. The server checks the media type, 10 MiB input limit, ZIP member count and compressed/uncompressed size limits, package structure, selected visible worksheet, row/column limits and version-specific headers. The parser uses `openpyxl` in read-only mode with XML hardening installed. Each actual sheet contains a formula-driven age column (`AGE IN AY'21` or `AGE IN AY'23`); only that selected column may contain formulas, and its saved cached result is used. A missing formula cache, formulas elsewhere, Excel error cells and numeric `Pris No.` values are rejected. Numeric IC/NRIC/contact cells are converted from the workbook's stored number and flagged because leading zeroes or long digits may already have been lost.
3. A preview reports source year and total, valid, invalid, existing, new and warning counts. Row errors/warnings identify only the workbook row, field and safe code; student values are not echoed. A nonblank class label without an active mapping reports `class_name: unmapped_class` and makes the whole batch ineligible to commit. `GET /api/v1/student-imports/{id}` returns that sanitized preview to the Operator who uploaded the batch.
4. The Operator chooses **Create new profiles only** or **Update existing profiles**. The first mode refuses a batch containing any identifier already in the database. The second explicitly updates matching `Pris No.` records and creates new ones. New identifiers require `NAME`, the selected sheet's class field, `CAT` and `STATUS`; blank fields on an existing profile preserve saved values. The 2021-only `VERIFY` detail is application-encrypted as `verification_note`; `ELECTIVE` is preserved as a profile academic selection. The 2021 sheet's missing 2023-only fields remain unset on create and preserve saved values on update. If numeric-cell warnings exist, the Operator must acknowledge them before either commit. Status changes append status history using the workbook's effective date or the current date when none is supplied.
5. Any invalid row blocks the batch. The commit rechecks all identifiers, captured profile versions, and class-mapping IDs/versions/targets; a changed mapping, identifier race or stale profile rejects the whole batch. Valid batches update profiles, status history, audit and batch outcome in one database transaction. A repeated commit returns the stored outcome without replaying changes.

## Controlled class mapping

IT Administrators manage source-label mappings under **Timetable / Schedule > Scheduling setup > Student intake class mappings**, alongside instructional-class setup. A mapping is unique for a workbook source and a Unicode-normalized, case-insensitive, whitespace-collapsed class label. The source selector distinguishes the 2021 and 2023 crosswalks even when both sheets use the same class label. Each mapping targets one active instructional class. The form supports creating a mapping, changing its target with an expected version, and deactivating/reactivating it; mappings are not deleted. Operators can read the mapping list but cannot edit it. Executives cannot access it.

Migration `20261028_0011` added the mapping table without rewriting existing student class values; `20261104_0019` expands its source constraint to both intake years. Import previews capture the mapping version and target; IT changes after preview require a fresh upload/preview before commit. No mapping is guessed from a similar class name. Existing profiles and historical attendance remain unchanged by mapping maintenance. Class entry remains free text in manual profiles; category, academic-year, and optional institution values use active reference catalogs. Intake preview validates category and any supplied academic year against active catalog values and binds those values to snapshots rechecked at commit.

## Protected staging

Migration `20261028_0010` adds `student_import_batches`; `20261104_0019` adds a source-year field and backfills existing batches as 2023 without changing their ciphertext. The original workbook bytes and parsed row payload are separately encrypted with the existing application encryption key before they are stored in PostgreSQL. New ciphertext has a key identifier; legacy Fernet ciphertext remains readable during key rotation, and the maintenance rotation tool covers both staged payloads. There is no endpoint to retrieve the raw workbook or staged values. Audit events contain source version, counts, field names, versions and row numbers only. An import batch is visible only to its creating Operator. Migration `20261104_0018` adds the IT-managed staging-payload retention lifecycle. `STUDENT_IMPORT_RETENTION_DAYS` is an environment setting from 0 through 3650 days, defaults to 0 (disabled), and is not editable from the application. IT Administrators and Superusers can view eligible counts and run a dry-run from Reference data; applying a purge additionally requires an explicit confirmation checkbox and a five-minute, actor-bound signed token returned by that dry-run. The server locks eligible batches and verifies the preview snapshot before clearing only encrypted source and staged-row payloads; any changed eligible set requires a new dry-run. It records actor-attributed audit events and marks uncommitted previews `EXPIRED`. Committed profiles, the aggregate import result, batch record and audit history remain available; replaying a completed signed request has no further effect. Expired previews cannot be committed and must be uploaded again. Operators retain access only to their own batch metadata.

Purging removes payloads from the live database logically. It does not establish immediate physical erasure from database write-ahead logs, snapshots, or backups; those copies follow the separately configured database backup retention and destruction procedures. Set a retention period only after the organization approves the required holding period.

## Boundaries and verification

IT/Superuser category, institution, and academic-year catalogs are enforced for supported profile fields. Intake preview validates `CAT` and a populated academic year against active catalog values, canonicalizes them, and captures each value's ID/version/name. Commit locks and rechecks those values so changed or archived references invalidate the preview. The workbooks have no institution column; imports leave existing institution unchanged and new profiles unassigned. Formulas outside the selected age column, formulas in dashboard sheets, reconciliation of historical values and workbook-report parity remain outside the import feature. Supplied values must satisfy the current profile schema; spreadsheet formatting is not a business rule. A preview is not a backup or a substitute for data reconciliation and sign-off. See [STUDENT_REFERENCE_CATALOGS.md](STUDENT_REFERENCE_CATALOGS.md) for controlled-value and historical-profile behavior.

API and migration tests cover actual 2021/2023 header maps, malformed packages, cached age formulas for both years, numeric identifier warnings and acknowledgement, duplicate workbook identifiers, sanitized preview, encryption at rest, ownership/role controls, create-only refusal, explicit updates, blank-field preservation, status history, stale profile/mapping previews, idempotent commit and transaction rollback. Migration coverage verifies existing payloads and ciphertext are preserved while old batches are identified as 2023. Chromium acceptance covers year selection, class mapping create/remap, Operator upload/preview/commit, and IT retention dry-run followed by explicit confirmation. CI runs these with PostgreSQL migration/model parity, security scans, browser checks and production-image validation.
